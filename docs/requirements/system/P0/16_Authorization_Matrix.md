## 1. Роли

### 1.1. Глобальные роли

| Роль | Область | Назначение |
|---|---|---|
| `app_admin` | Приложение | Администратор приложения: пользователи, роли, настройки, исполнители, все проекты, privileged audit |

Отдельной роли `auditor` в текущих постановках **нет**. Чтение аудита доступно `app_admin`; владелец видит только аудит своих проектов. Если нужна отдельная read-only роль аудитора — это отдельное решение и ADR.

### 1.2. Проектные роли

| Роль | Назначение |
|---|---|
| `project_owner` | Владелец проекта: настройки, участники, архив, удаление, аудит, передача владения |
| `project_manager` | Руководитель: план, задачи, зависимости, импорт, модерация комментариев |
| `project_editor` | Редактор: задачи, сроки, зависимости, комментарии |
| `project_participant` | Участник: только назначенные задачи и комментарии |
| `project_viewer` | Наблюдатель: просмотр, экспорт/PDF, без изменений |

Роли фиксированные, пользовательские роли не создаются. В проекте — одна роль на пользователя.

### 1.3. Базовые принципы

1. `app_admin` — глобальный административный доступ ко всем проектам (ADR-008).
2. Обычный пользователь видит только проекты, где он участник.
3. UI скрывает недоступные действия, но сервер проверяет права всегда.
4. Проверка прав не кэшируется надолго.
5. Object-level проверка выполняется после role-check.
6. 403 и 404 не должны раскрывать существование чужих объектов.
7. Все административные изменения фиксируются в аудите.
8. Клиент не передает свою роль как доверенные данные.

Создание проекта — глобальная возможность любого активного авторизованного пользователя; она описана в §2, а не в проектной роли. Создатель становится владельцем; `app_admin` может выбрать другого владельца.

### 3.1. Ограничения по диаграммам

- Диаграмма принадлежит проекту; cross-project доступ запрещен.
- `diagram.create/update/delete` — логические permissions; в текущем seed их нет. Нужно либо добавить в seed, либо явно маппить на `project.update`/`project.task.*` (см. §7).
- Импорт заменяет диаграмму только после подтверждения и проверки файла (см. ADR-011).
- Печать/PDF использует `project.export`; отдельный `project.print` не вводится.

## 4. Object-level правила

### 4.1. Участник и назначенные задачи

Участник может редактировать задачу, если он указан:

- ответственным;
- исполнителем;
- соисполнителем (до двух).

Если назначение задано как справочный исполнитель без связи с пользователем, доступа по этому назначению нет. Связь исполнитель → пользователь проверяется через User & Access.

### 4.2. Комментарии

- Автор может редактировать/удалять свой комментарий.
- `app_admin`, владелец и руководитель могут модерировать любой комментарий.
- Редактор и участник — только свой.
- Наблюдатель не комментирует.
- Удаление — мягкое.

### 4.3. Владелец проекта

- Владелец один.
- Передача владения: старый владелец становится `project_manager`, новый — `project_owner`.
- Передача идемпотентна и аудируется.
- Нельзя удалить пользователя, владеющего проектами, без предварительной передачи владения.

### 4.4. Архив и удаление

- Удаление только из архива.
- Восстановление возвращает в архив.
- Удаленный проект доступен 1 год.
- Хранится только последнее архивное состояние.
- `app_admin` и `project_owner` — только они.

### 4.5. Аудит

- `app_admin` — общий и privileged журналы.
- `project_owner` — только аудит своих проектов.
- `project_manager`, editor, participant, viewer — не видят аудит проекта, если это не решено отдельно.
- Экспорт аудита отсутствует.
- Privileged journal недоступен владельцу проекта.

### 4.6. Исполнители

- `app_admin` управляет каталогом и связывает исполнителя с пользователем.
- `project_owner` может управлять каталогом в рамках своих проектов, но не связывать с пользователем.
- Остальные роли каталог не изменяют.
- Удаление исполнителя не удаляет задачи; в задачах показывается «Исполнитель не найден».

## 6. Enforcement

### 6.1. Порядок проверки

1. Аутентификация: сессия, срок, активный статус.
2. Глобальная роль: доступ к admin-операциям.
3. Проект: membership или `app_admin` override.
4. Проектная роль: permission.
5. Object-level: назначение, автор комментария, владелец.
6. Бизнес-правила: архив, удаление, лимиты.
7. Аудит.

### 6.2. Где проверяется

- API Gateway: только auth, CSRF, rate limit, маршрутизация.
- User & Access: пользователи, роли, membership, `CheckProjectPermission`, `ListAccessibleProjectIds`.
- Project / Diagram: каждая операция с проектом/диаграммой.
- Audit: доступ к журналам.
- Frontend: скрывает действия, но не является защитой.

### 6.3. Ошибки

| Ситуация | Ответ |
|---|---|
| Нет сессии | `401` |
| Нет глобальной роли | `403` |
| Нет membership | `403` или `404` по правилу анти-энумерации |
| Нет project permission | `403` |
| Нет object-level доступа | `403` |
| Объект не существует | `404` |
| Последний администратор | `409`/`FAILED_PRECONDITION` |
| Удаление владельца проектов | `409 ownership_transfer_required` |

## 7. Расхождения и обязательные правки

| # | Расхождение | Решение |
|---|---|---|
| 1 | В seed `project.create` есть только у `app_admin`, но создавать может любой активный пользователь | Проверять active user в Project Service; `project.create` не должен быть только админским |
| 2 | Нет permission `project.owner.transfer` | Добавлено в seed; проверять в Project Service |
| 3 | Нет permissions `diagram.create/update/delete` | Добавлены в seed; проверить маппинг API |
| 4 | `app_admin` в проектных матрицах указан «Да», но membership-проверка этого не отражает | Реализовать override в `CheckProjectPermission`/`ListAccessibleProjectIds` (ADR-008) |
| 5 | `project.task.edit.assigned` не должен давать доступ к чужим задачам | Проверять назначение после permission |
| 6 | Владелец видит `/audit`, но не должен видеть чужие проекты | `/audit` фильтруется по accessible projects |
| 7 | Роль `auditor` упоминалась в обсуждениях, но отсутствует в модели | Не вводить без ADR; сейчас privileged audit — только `app_admin` |
| 8 | Админ создает проект на другого владельца | Владелец — выбранный пользователь; админ не становится владельцем |
| 9 | Админ без membership видит проект | Это разрешено ADR-008; UI показывает режим расширенного доступа |
| 10 | `project.comment.moderate` у редактора/участника | Ограничить object-level: только свой комментарий |

## 8. Тестовая матрица

Обязательные кейсы:

1. `app_admin` без membership видит и редактирует проект.
2. Обычный пользователь без membership получает 403/404.
3. Владелец управляет участниками; руководитель — нет.
4. Руководитель создает/удаляет задачи; редактор удалять не может.
5. Редактор управляет зависимостями; участник — нет.
6. Участник редактирует назначенную задачу; чужую — нет.
7. Участник с назначением через несвязанного исполнителя не получает доступ.
8. Наблюдатель экспортирует, но не комментирует и не меняет.
9. Автор комментария редактирует свой; чужой — только модератор.
10. Передача владения: старый owner → manager, новый → owner.
11. Удаление пользователя с проектами отклоняется до передачи владения.
12. Последний `app_admin` не может быть снят.
13. Владелец видит аудит только своих проектов.
14. `app_admin` видит privileged audit; владелец — нет.
15. Импорт: только admin/owner/manager.
16. Экспорт: viewer может, participant — нет.
17. Удаление проекта только из архива.
18. Восстановление возвращает в архив.
19. Админ создает проект на другого владельца; владелец — целевой пользователь.
20. Все проверки повторяются на сервере при прямом API-вызове.

## 9. Критерии приемки

1. Матрица совпадает с seed и сервисными проверками.
2. `app_admin` override реализован и покрыт тестами.
3. `project.create` доступен активному пользователю.
4. `project.owner.transfer` и `diagram.*` permissions добавлены или явно замаплены.
5. Участник не может выйти за пределы назначенных задач.
6. Владелец не видит чужие проекты и чужой аудит.
7. Privileged audit доступен только `app_admin`.
8. UI скрывает действия, но API возвращает 403 при обходе.
9. Все 20 тестовых кейсов автоматизированы.
10. Расхождения из §7 закрыты или оформлены ADR.
