## 1. Решение о границах MVP

MVP — это первый production-релиз, в котором команда может полностью работать с серверным планом:

- войти в систему;
- управлять пользователями и ролями;
- создать проект и диаграмму;
- вести направления, задачи, подзадачи, сроки, зависимости и комментарии;
- видеть изменения других участников;
- импортировать и экспортировать план;
- видеть аудит действий;
- администрировать пользователей и настройки.

MVP **не включает** полноценный Notification Service, Telegram, мобильную версию, dark theme и аналитику. Исключение — ранний Notification Service в минимальном объеме: транзакционные auth-письма (подтверждение email и сброс пароля).

### 1.1. Релизы

| Релиз | Содержание | Ориентир |
|---|---|---|
| **R1 / MVP** | Auth, пользователи и роли, проекты, Гант, комментарии, импорт/экспорт, Sync, Audit, SSR-интерфейс, админка, минимальный Notification Service для auth-писем | 18–24 недели по плану + 1–2 недели на минимальный Notification Service |
| **R2 / Notifications** | In-app уведомления, email-уведомления, настройки, напоминания, журнал доставки | +5–7 недель |
| **R3 / Telegram и эксплуатация** | Telegram-бот, привязка, доставка, нагрузочная и production-эксплуатация | +2–3 недели Telegram |
| **После MVP** | Мобильная адаптация, dark theme, offline-first, аналитика, расширенные интеграции | отдельные этапы |

### 1.2. В MVP входит

- Регистрация, вход, выход, восстановление пароля, подтверждение email, сессии.
- Профиль, смена пароля, список и отзыв сессий.
- Администрирование пользователей, блокировка, удаление, глобальные роли, bootstrap администратора.
- Каталог исполнителей и связь исполнитель ↔ пользователь.
- Проекты: создание, список, архив, восстановление, удаление, настройки, участники, приглашения, передача владения.
- Диаграммы и Гант: направления, задачи, подзадачи, ответственные, исполнители, до двух соисполнителей, сроки, рабочие дни, праздники, статусы, прогресс, приоритеты, Jira-номер как текст.
- Зависимости, проверка циклов, критический путь.
- Комментарии и модерация.
- Ревизии и история изменений.
- Импорт v2 и legacy v9/v1, экспорт JSON/CSV/PDF, печать.
- Sync/Realtime: подписка, snapshot, изменения, reconnect, конфликты.
- Аудит: общий, проектный, привилегированный; без экспорта.
- SSR-интерфейс для Auth, Projects, Gantt, Audit и Admin; Notifications — R2.
- Минимальный Notification Service: `SendAuthEmail`, шаблоны verification/reset, SMTP/Mailpit, retry и журнал доставки.
- Базовые loading/empty/error/no-access состояния.
- Локальный Docker Compose, CI, codegen, contract tests, observability baseline.

### 1.3. Не входит в MVP

- Полноценный Notification Service, in-app центр уведомлений, email-уведомления по задачам, напоминания.
- Telegram-бот и привязка Telegram.
- Мобильная версия и touch-first UX.
- Dark theme.
- SSO, корпоративные каталоги, Teams/Slack.
- Jira-интеграция; только поле «Номер задачи Jira».
- Выгрузка аудита.
- Пользовательские роли и кастомные permission sets.
- Более одного владельца проекта.
- Более двух соисполнителей.
- Offline-first редактирование и очередь изменений без сети.
- Аналитика, BI, read replica.
- Автоматическая миграция localStorage без участия пользователя.

> **Важно:** экран `/notifications` и настройки уведомлений относятся к R2. В MVP Notification Service работает только для `SendAuthEmail` (verification/reset); in-app уведомления, email по задачам, напоминания и Telegram — R2/R3.

## 2. Роли и пользователи MVP

| Роль | Что делает в MVP |
|---|---|
| Гость | Регистрация, вход, восстановление пароля |
| Авторизованный пользователь | Создает проекты, работает в проектах, где состоит |
| `app_admin` | Управляет пользователями, ролями, настройками, исполнителями, привилегированным аудитом |
| `project_owner` | Управляет проектом, участниками, архивом, удалением, аудитом проекта |
| `project_manager` | Ведет план, задачи, зависимости, импорт, модерацию комментариев |
| `project_editor` | Редактирует задачи, сроки, зависимости, комментарии |
| `project_participant` | Обновляет только назначенные задачи, комментирует |
| `project_viewer` | Смотрит план, экспорт/PDF, без изменений |

Точная матрица прав — в `P0/16_Authorization_Matrix.md`.

## 5. Acceptance criteria для P0-среза

### AUTH-01 — Регистрация

- Email нормализуется, проверяется на формат и уникальность.
- Пароль 8–128 символов; hash Argon2id/bcrypt; пароль не логируется.
- ФИО — три обязательных поля: фамилия, имя, отчество.
- Timezone по умолчанию `Europe/Moscow`; locale — `ru-RU`.
- Consent обязателен; без него регистрация отклоняется.
- До подтверждения email пользователь не получает полноценную сессию.
- Ошибки не раскрывают существование email.
- Создается аудит `user.registered`.

### AUTH-03 — Вход и сессия

- Успешный вход создает сессию и `Set-Cookie`.
- Cookie: `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, без `Domain`.
- Обычная сессия: 1 час absolute, 10 минут idle.
- Remember: 30 дней absolute, 7 дней idle.
- Не более двух активных сессий; третья отклоняется с `session_limit_reached`.
- `Logout` удаляет сессию и cookie.
- При истекшей сессии frontend получает 401 и ведет на login.
- Аудит: `auth.login.succeeded`, `auth.login.failed`, `auth.logout`.

### PRJ-02 — Создание проекта

- Любой активный авторизованный пользователь может создать проект.
- Создатель становится `project_owner`; создается membership.
- `app_admin` может выбрать владельца из активных пользователей.
- Если админ создает проект на другого владельца, владельцем становится выбранный пользователь; админ не становится владельцем, но сохраняет административный доступ по ADR-008.
- Название обязательно; описание опционально.
- Создание и назначение владельца идемпотентны.
- При ошибке создания владельца проект не создается.
- Аудит: `project.created`, `project.owner.assigned`.

### PRJ-04 — Архив, restore, delete

- Удаление доступно только из архива.
- Восстановление возвращает проект в архив.
- Удаленный проект доступен в `deleted` 1 год.
- Хранится только последнее архивное состояние.
- Удаление/восстановление — только `app_admin` или `project_owner`.
- Аудит: `project.archived`, `project.restored`, `project.deleted`.
- После 1 года — окончательная очистка.

### DIA-06 — Зависимости и критический путь

- Зависимость хранит `fromTaskId`, `toTaskId`, тип.
- Цикл отклоняется с понятной ошибкой.
- Нельзя создать зависимость на задачу другого проекта/диаграммы.
- Критический путь рассчитывается по текущим срокам.
- Изменение зависимости фиксируется в ревизии и аудите.
- UI показывает критический путь контуром + легендой, не только цветом.

### SYNC-03 — Конфликт

- При reconnect клиент получает актуальный snapshot.
- При конфликте версий сервер возвращает `409`/`snapshot_required`.
- Пользователь видит banner с выбором: обновить / сохранить копию / отменить.
- Молчаливая перезапись запрещена.
- Конфликт и разрешение фиксируются в аудите.

### AUD-02 — Привилегированный аудит

- `app_admin` видит общий и privileged журналы.
- `project_owner` видит только аудит своих проектов.
- Фильтры: период, пользователь, действие, проект, важность.
- Детали: before/after, metadata, request/correlation ID.
- Экспорта нет.
- Privileged journal недоступен остальным ролям.

## 8. Definition of Ready

История готова к разработке, если:

- есть user story и acceptance criteria;
- определены роли и права;
- есть API/proto/event contract или явно указано, что он создается в этой истории;
- описаны состояния loading/empty/error/no-access;
- определены audit events;
- понятны зависимости и feature flag;
- есть тестовые данные или способ их создать;
- оценена командой;
- нет открытых продуктовых вопросов, влияющих на реализацию.

## 9. Definition of Done

История готова, если:

- код в main, CI зеленый;
- unit + contract/integration tests;
- проверены права и негативные сценарии;
- аудит пишется;
- ошибки RFC 7807;
- UI соответствует tokens/prototype и имеет состояния;
- accessibility-базис выполнен;
- документация/OpenAPI/proto обновлены;
- нет P0/P1 дефектов;
- feature flag/rollback предусмотрены;
- demo/acceptance проведены.

## 10. Критерии выхода MVP

1. Пилотный пользователь проходит путь: регистрация → подтверждение email → проект → диаграмма → задачи → зависимости → комментарий → импорт/экспорт.
2. Два пользователя одновременно работают с диаграммой; изменения синхронизируются; конфликт не теряет данные.
3. Все роли из матрицы проверены автотестами.
4. Аудит содержит действия по auth, проектам, плану, ролям и админке.
5. Импорт v9/v1 и v2 проверен на реальных примерах.
6. Восстановление удаленного проекта работает; срок 1 год.
7. SLO baseline и алерты работают; backup/restore проверен.
8. Accessibility-базис и keyboard-сценарии приняты.
9. Нет открытых P0-дефектов и известных критичных рисков.
10. Проведена пилотная миграция и обучение.

## 11. Открытые вопросы

1. **Audit `/audit`:** владелец видит только свои проекты; нужен ли сводный экран по всем доступным проектам.
2. **Импорт:** заменяет диаграмму или создает новую — ADR-011.
3. **`app_admin` и проекты:** принято ADR-008 — глобальный административный доступ; нужен ли отдельный read-only support mode, решается отдельно.
4. **Auth-письма:** принято ADR-010 — ранний Notification Service в минимальном объеме.
