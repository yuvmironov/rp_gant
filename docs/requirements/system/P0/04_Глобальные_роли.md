# P0: управление глобальными ролями
## SMART OATI

**Версия:** 1.0  
**Дата:** 2026-10-28

---

## 1. Проблема

В User & Access отсутствовал метод изменения глобальных ролей после создания пользователя.

Это блокировало:

- назначение и снятие `app_admin`;
- управление администраторами;
- полноценный привилегированный аудит;
- безопасное развертывание.

---

## 2. Решение

Добавлен метод:

```text
UserService.SetUserGlobalRoles
```

Семантика:

- заменяет **весь** набор глобальных ролей пользователя;
- доступен только `app_admin`;
- не позволяет снять `app_admin` с последнего администратора;
- не позволяет администратору снять `app_admin` с самого себя, если он последний;
- изменения выполняются в одной транзакции;
- действие фиксируется в аудите как `user.roles.updated`;
- сессии пользователя не отзываются автоматически;
- при снятии `app_admin` следующие проверки прав уже не дают административных прав.

---

## 3. gRPC

```text
rpc SetUserGlobalRoles(SetUserGlobalRolesRequest) returns (SetUserGlobalRolesResponse);
```

Запрос:

- `user_id`;
- `roles` — полный новый набор;
- `actor_user_id`.

Ответ:

- `user`;
- `roles`.

Ошибки:

- `PERMISSION_DENIED` — вызывающий не администратор;
- `NOT_FOUND` — пользователь не найден;
- `FAILED_PRECONDITION` — попытка снять последнего администратора;
- `INVALID_ARGUMENT` — неизвестная роль.

---

## 4. REST

```text
PUT /api/v1/users/{userId}/roles
```

Тело:

```json
{
  "roles": ["app_admin"]
}
```

Требования:

- cookie-сессия;
- `X-CSRF-Token`;
- `Idempotency-Key`;
- только администратор.

Ответ — обновленный пользователь.

---

## 5. Bootstrap первого администратора

Первый `app_admin` не создается seed-скриптом с паролем.

Порядок:

1. Развернуть User DB.
2. Применить миграции и seed.
3. Зарегистрировать первого пользователя через приложение.
4. Подтвердить email.
5. Выполнить одноразовый bootstrap-скрипт с `BOOTSTRAP_ADMIN_EMAIL`.
6. Скрипт добавляет `app_admin` и пишет аудит.
7. После этого дальнейшие роли назначаются через `SetUserGlobalRoles`.

Bootstrap-скрипт должен:

- работать только при отсутствии `app_admin`;
- требовать явного email;
- не логировать пароль;
- быть идемпотентным;
- завершаться ошибкой, если администратор уже есть.

---

## 6. Аудит

Событие:

```text
user.roles.updated
```

Обязательные поля:

- `actorUserId`;
- `targetUserId`;
- `previousRoles`;
- `newRoles`;
- `occurredAt`.

Событие попадает:

- в общий аудит;
- в привилегированный аудит, если актор — `app_admin`.

---

## 7. Тесты

1. Администратор назначает `app_admin`.
2. Администратор снимает `app_admin`.
3. Нельзя снять последнего `app_admin`.
4. Нельзя снять `app_admin` с себя, если он последний.
5. Не-администратор получает `403`.
6. Неизвестная роль — `400`.
7. Несуществующий пользователь — `404`.
8. Повтор с тем же `Idempotency-Key` не создает дубль.
9. Аудит содержит old/new roles.
10. Bootstrap создает первого администратора ровно один раз.

---

## 8. Критерии приемки

1. Метод есть в proto.
2. Метод есть в OpenAPI.
3. Проверка последнего администратора реализована.
4. Аудит фиксирует изменение.
5. Bootstrap-процедура описана.
6. Сессии не ломаются при смене роли.
7. Все тесты проходят.
