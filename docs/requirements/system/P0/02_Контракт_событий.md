# P0: контракт событий
## SMART OATI

**Версия:** 1.0  
**Дата исходного документа:** 2026-10-28

> Payload-примеры ниже — проектный snapshot. Для текущего envelope, типов и схем используйте `events/schemas/`, `events/event-types.json` и [`docs/IMPLEMENTATION-STATUS.md`](../../../IMPLEMENTATION-STATUS.md).

---

## 1. Назначение

Единый контракт асинхронных событий между backend-сервисами.

Артефакты:

- `events/asyncapi.yaml`;
- `events/event-types.json`;
- `events/schemas/event-envelope.schema.json`;
- `events/schemas/payloads.schema.json`;
- `events/schemas/diagram-changed.schema.json`;
- `events/schemas/auth-email-requested.schema.json`.

---

## 2. EventEnvelope

Текущая схема требует эти поля в snake_case:

- `event_id` — UUID;
- `event_type` — строка;
- `schema_version` — целое, начиная с 1;
- `occurred_at` — date-time;
- `source_service` — `user | project`;
- `actor_user_id`, `actor_roles`;
- `project_id`, `diagram_id`;
- `entity_type`, `entity_id`;
- `payload` — объект.

Дополнительные nullable-поля схемы: `request_id`, `correlation_id`.

### 2.1. Реализационный статус actor roles

JSON Schema требует `actor_roles`. User Service записывает в outbox глобальные и активные project roles актёра; Project Service фиксирует роль из успешного `CheckProjectPermission`. Publishers переносят snapshot в envelope, Audit consumer сохраняет его. Для операций, меняющих собственные роли актёра, producer должен передать snapshot до мутации. Покрытие producer-side serialization проверяется unit tests; DB-backed staging acceptance описана в `docs/IMPLEMENTATION-STATUS.md`.

## 3. Именование

Формат:

```text
<domain>.<entity>.<action>
```

Примеры:

- `project.member.removed`;
- `diagram.import.completed`;
- `dependency.violated`;
- `diagram.critical_path.changed`.

Запрещено менять смысл существующего event type. Новый смысл — новый тип.

---

## 4. Каталог

Полный каталог — `events/event-types.json`.

Каталог содержит 68 типов событий; число `$defs` payload в текущей схеме — 79. Это разные счётчики. Для точных данных используйте `events/event-types.json` и `events/schemas/payloads.schema.json`.

Группы:

- user/auth;
- project;
- project members/invitations;
- executors;
- diagram/plan;
- dependencies/comments;
- import;
- notifications/auth email/Telegram;
- settings.

Для каждого события указаны producer и consumers.

## 6. Outbox

Каждый сервис пишет событие в `events.outbox_events` в той же транзакции, что и бизнес-изменение.

Поля:

- `id`;
- `aggregate_type`;
- `aggregate_id`;
- `event_type`;
- `payload`;
- `headers`;
- `occurred_at`;
- `published_at`;
- `retry_count`;
- `last_error`.

Relay:

1. читает `published_at IS NULL`;
2. публикует в брокер;
3. ставит `published_at`;
4. при ошибке увеличивает `retry_count`;
5. после лимита — очередь ошибок.

---

## 7. Доставка

- at-least-once;
- порядок гарантируется по `diagramId + revision` для `diagram.changed`;
- остальные события не гарантируют глобальный порядок;
- consumers идемпотентны по `eventId`;
- повторная доставка не создает дубликаты;
- события хранятся в брокере не менее 7 дней;
- `diagram_changes` хранятся 2 месяца для backfill.

---

## 8. Версионирование

- `schemaVersion` — версия payload;
- добавление необязательных полей — совместимо;
- удаление/переименование — новая версия;
- consumer должен игнорировать неизвестные поля;
- producer не удаляет поля без периода совместимости.

---

## 9. Критерии приемки

1. Все события соответствуют EventEnvelope.
2. `actorRoles` передается для пользовательских действий.
3. `diagram.changed` содержит полный объект.
4. `revision` монотонна в пределах диаграммы.
5. `dependency.violated` и `diagram.critical_path.changed` публикуются.
6. `comment.created` содержит `mentionedUserIds`.
7. Outbox пишется в одной транзакции.
8. Relay публикует и ретраит.
9. Consumers идемпотентны.
10. Все event types есть в каталоге.
11. Producers/consumers совпадают с каталогом.
12. События не содержат PII и полного текста комментариев.
