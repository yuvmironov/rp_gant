# P0: контракт событий
## SMART OATI

**Версия:** 1.0  
**Дата:** 2026-10-28

---

## 1. Назначение

Единый контракт асинхронных событий между backend-сервисами.

Артефакты:

- `Исходные кодв/events/asyncapi.yaml`;
- `Исходные кодв/events/event-types.json`;
- `Исходные кодв/events/schemas/event-envelope.schema.json`;
- `Исходные кодв/events/schemas/diagram-changed.schema.json`;
- `Исходные кодв/events/schemas/auth-email-requested.schema.json`.

---

## 2. EventEnvelope

Обязательные поля:

- `eventId` — UUID;
- `eventType` — строка;
- `schemaVersion` — целое, начиная с 1;
- `occurredAt` — RFC 3339;
- `sourceService` — `user | project | notification | audit`;
- `payload` — объект.

Дополнительные поля:

- `actorUserId`;
- `actorRoles`;
- `projectId`;
- `diagramId`;
- `entityType`;
- `entityId`;
- `requestId`;
- `correlationId`.

### 2.1. Обязательное правило

Все producers обязаны передавать `actorRoles` для действий пользователя. Это необходимо для:

- привилегированного аудита;
- проверки прав;
- разбора инцидентов.

Если `actorRoles` отсутствует, событие считается неполным; Audit может запросить роли у User & Access, но это fallback, а не норма.

---

## 3. Именование

Формат:

```text
<domain>.<entity>.<action>
```

Примеры:

- `project.member.removed`;
- `diagram.import.completed`;
- `dependency.violated`;
- `diagram.critical_path.changed`.

Запрещено менять смысл существующего event type. Новый смысл — новый тип.

---

## 4. Каталог

Полный каталог — `events/event-types.json`.

Полные payload-схемы всех 64 событий — `11_Полные_payload_событий.md` и `events/schemas/payloads.schema.json`.

Группы:

- user/auth;
- project;
- project members/invitations;
- executors;
- diagram/plan;
- dependencies/comments;
- import;
- notifications/auth email/Telegram;
- settings.

Для каждого события указаны producer и consumers.

## 6. Outbox

Каждый сервис пишет событие в `events.outbox_events` в той же транзакции, что и бизнес-изменение.

Поля:

- `id`;
- `aggregate_type`;
- `aggregate_id`;
- `event_type`;
- `payload`;
- `headers`;
- `occurred_at`;
- `published_at`;
- `retry_count`;
- `last_error`.

Relay:

1. читает `published_at IS NULL`;
2. публикует в брокер;
3. ставит `published_at`;
4. при ошибке увеличивает `retry_count`;
5. после лимита — очередь ошибок.

---

## 7. Доставка

- at-least-once;
- порядок гарантируется по `diagramId + revision` для `diagram.changed`;
- остальные события не гарантируют глобальный порядок;
- consumers идемпотентны по `eventId`;
- повторная доставка не создает дубликаты;
- события хранятся в брокере не менее 7 дней;
- `diagram_changes` хранятся 2 месяца для backfill.

---

## 8. Версионирование

- `schemaVersion` — версия payload;
- добавление необязательных полей — совместимо;
- удаление/переименование — новая версия;
- consumer должен игнорировать неизвестные поля;
- producer не удаляет поля без периода совместимости.

---

## 9. Критерии приемки

1. Все события соответствуют EventEnvelope.
2. `actorRoles` передается для пользовательских действий.
3. `diagram.changed` содержит полный объект.
4. `revision` монотонна в пределах диаграммы.
5. `dependency.violated` и `diagram.critical_path.changed` публикуются.
6. `comment.created` содержит `mentionedUserIds`.
7. Outbox пишется в одной транзакции.
8. Relay публикует и ретраит.
9. Consumers идемпотентны.
10. Все event types есть в каталоге.
11. Producers/consumers совпадают с каталогом.
12. События не содержат PII и полного текста комментариев.
