# План реализации серверной версии и уведомлений
## «Диаграмма Ганта — проект SMART OATI»

**Версия плана:** 1.6  
**Дата:** 2026-10-27  
**Основание:** текущая реализация (локальный однопользовательский режим), системная постановка версии 9, `../changelog.md`

> План обновлён с учётом ограничений: приложение работает самостоятельно; уведомления — только внутренние, email и Telegram; Jira-интеграция не выполняется, сохраняется только поле номера задачи; backend — Node.js на JavaScript без TypeScript в **микросервисной архитектуре**; frontend — Vue 3 + Nuxt 3 с SSR на JavaScript. Все данные пользователей вынесены в отдельный **User & Access Service**. Синхронное взаимодействие backend-сервисов — только по **gRPC**; REST между backend-сервисами запрещён.
>
> **Приняты решения:** один кластер PostgreSQL с отдельными БД и отдельными схемами; полное удаление пользователей; хранение истории изменений, аудита, уведомлений и журнала доставки — 2 месяца; до двух соисполнителей на задачу; состояние сворачивания и фильтры на сервере не хранятся; шаблоны проектов и диаграмм не предусмотрены; проект архивируется перед удалением, удаленный проект можно восстановить в течение 1 года; хранится только последнее архивное состояние; средний уровень шифрования; отдельная read-only роль для аналитики на основном кластере без read replica; материализованные представления и маскирование данных для аналитики не требуются.
>
> **Статус:** этот план версии 1.6 — исторический проектный документ. Приоритет имеют принятые ADR, текущие контракты и код. В частности, ADR-001 выбрал Kafka, ADR-004 — cookie-сессии в User Service (не Redis), а текущий `apps/frontend` собран с `ssr: false`. В Gateway вызовы User/Project идут по gRPC, Notification/Audit — по внутреннему HTTP. Сводка реализации: [`docs/IMPLEMENTATION-STATUS.md`](../../IMPLEMENTATION-STATUS.md).

## 1. Цель

Перевести приложение из локального режима в самостоятельный многопользовательский веб-сервис с серверным хранением, совместной работой и уведомлениями. Backend строится как набор небольших независимо развертываемых сервисов.

Итоговый результат:

- план хранится на сервере и доступен с разных устройств;
- пользователи регистрируются и входят в приложение самостоятельно;
- все пользовательские данные, роли и участники проектов находятся в отдельном сервисе;
- права доступа определяются ролью и участием в проекте;
- изменения синхронизируются между устройствами и участниками;
- участники получают внутренние уведомления, письма на email и сообщения в Telegram;
- в карточке задачи сохраняется номер задачи Jira как справочная информация, без обмена данными с Jira;
- backend состоит из независимых сервисов, синхронно общающихся по gRPC.

## 2. Рамки и допущения

### 2.1. Что входит в план

1. Микросервисный backend на Node.js.
2. Отдельный User & Access Service для пользователей, ролей и участников проектов.
3. Серверная база данных и синхронизация между устройствами.
4. Собственная авторизация и роли пользователей.
5. Внутренние уведомления, email и Telegram.
6. Перевод frontend на Vue 3 + Nuxt 3 с SSR.
7. Миграция существующих локальных планов в серверную версию.

### 2.2. Что не входит в план

- интеграция с Jira (сохраняется только номер задачи в карточке);
- мобильное приложение;
- учет бюджета, трудозатрат и стоимости;
- управление ресурсами и выравнивание загрузки;
- baseline-планы и версионирование плана;
- другие каналы уведомлений, кроме внутренних, email и Telegram.

### 2.3. Допущения для оценки

- Приложение разворачивается самостоятельно: облако, VPS или собственный сервер.
- Пользователи создаются регистрацией или приглашением администратора приложения.
- Для email используется собственный SMTP-ящик или внешний почтовый сервис.
- Для Telegram создается собственный бот.
- Backend — Node.js на JavaScript, без TypeScript; каждый сервис — отдельный процесс и отдельный контейнер.
- Frontend — Vue 3 + Nuxt 3 с SSR.
- Внутренние синхронные вызовы — только gRPC/protobuf.
- Команда: 1 архитектор/лид, 3 backend-разработчика, 2 frontend-разработчика, 1 QA, 1 DevOps.
- Работа ведется итерациями по 2 недели.
- Оценки предварительные, допуск ±30%.

## 3. Целевая архитектура

### 3.1. Общая схема

```text
Браузер
  ↓ HTTPS
Frontend: Vue 3 + Nuxt 3 (SSR)
  ↓ REST/JSON (публичный API)
API Gateway
  ├── User & Access Service
  ├── Project / Diagram Service
  ├── Notification Service
  ├── Sync / Realtime Service
  └── Audit Service
        ↓ gRPC между backend-сервисами
        ↓ асинхронные события через брокер
  PostgreSQL (по сервисам) + Redis + брокер сообщений
        ↓
  SMTP (email) + Telegram Bot API
```

Frontend и backend — отдельные приложения. Backend состоит из нескольких независимо развертываемых сервисов.

### 3.2. Backend: Node.js, JavaScript, без TypeScript (микросервисы)

#### 3.2.1. API Gateway

- Единая точка входа для frontend.
- Публичный API — REST/JSON.
- Маршрутизация запросов к сервисам по gRPC.
- Проверка аутентификации и базовых прав.
- Ограничение частоты запросов.
- Сквозной идентификатор запроса для трассировки.
- CORS и работа с cookie-сессией.
- Не содержит бизнес-логики плана.
- Не хранит пользовательские данные.

#### 3.2.2. User & Access Service

Единственный сервис, который владеет всем, что связано с пользователями.

- Регистрация и вход пользователей.
- Пароли, подтверждение email, восстановление пароля.
- Сессии и токены.
- Профили пользователей.
- Глобальные роли и статус пользователя.
- Приглашения в приложение.
- Участники проектов.
- Роли участников в проектах.
- Каталог исполнителей.
- Контакты пользователей: email, Telegram.
- Связь пользователя с исполнителем.
- Проверка членства в проекте и прав.
- Собственная БД пользователей, ролей, участников и исполнителей.

Сервис не хранит проекты, диаграммы, задачи, зависимости и комментарии.

#### 3.2.3. Project / Diagram Service

- Проекты (с ссылками на пользователей по ID).
- Архивирование проекта перед удалением; удаление только из архива.
- Восстановление удаленного проекта в течение 1 года; хранение только последнего архивного состояния.
- Очистка проекта после истечения срока хранения.
- Диаграммы, направления, задачи и подзадачи.
- Сроки, статусы, проценты, приоритеты.
- Зависимости и стили связей.
- Комментарии (с автором по ID).
- Праздники и режим дней.
- Признаки БП/СП.
- Номер задачи Jira как текстовое поле.
- Ревизии диаграмм и задач.
- Экспорт JSON/CSV.
- Собственная БД плана.

Сервис **не хранит** профили пользователей, имена, email, Telegram, участников проектов, роли, приглашения и каталог исполнителей. В задачах и комментариях хранятся только непрозрачные идентификаторы пользователей и исполнителей.

#### 3.2.4. Sync / Realtime Service

- Подписка клиентов на изменения диаграммы.
- WebSocket/SSE-соединения.
- Рассылка событий об изменениях.
- Поддержка нескольких устройств и участников.
- Presence (кто смотрит диаграмму) — опционально.
- Не хранит бизнес-данные; использует Redis и события сервисов.
- Не хранит профили пользователей; использует идентификаторы из контекста авторизации.

#### 3.2.5. Notification Service

- Внутренние уведомления.
- Email через SMTP.
- Telegram через собственного бота.
- Настройки уведомлений пользователя.
- Напоминания о сроках и дайджесты.
- Журнал доставки и повторные попытки.
- Планировщик заданий.
- Получает контакты и сведения о пользователях из User & Access Service по gRPC.

#### 3.2.6. Audit Service

- Централизованный журнал действий.
- Входы, изменения плана, права, уведомления.
- Хранит идентификаторы пользователей; сведения о них получает из User & Access Service по gRPC.
- Общий журнал хранится 2 месяца.
- Отдельный привилегированный журнал всех действий администраторов приложения хранится 2 года.
- Поиск аудита; выгрузка журнала не предусмотрена в первой версии.
- Интерфейс аудита описывается отдельно в постановке frontend.

### 3.3. Взаимодействие сервисов

- **Frontend → API Gateway:** REST/JSON, публичный API.
- **Целевая схема:** API Gateway → backend-сервисы и межсервисные вызовы по gRPC/protobuf, без агрегации.
- **Фактическая схема Gateway:** User и Project вызываются по gRPC; Notification и Audit — внутренним HTTP-клиентом.
- REST/HTTP между backend-сервисами не является утверждённым целевым контрактом; фактическое исключение описано в `docs/IMPLEMENTATION-STATUS.md`.
- Асинхронные события — через Kafka по ADR-001; локальный Compose использует KRaft.
- API Gateway транслирует публичный REST/JSON в вызовы backend; в текущей реализации для User/Project это gRPC, для Notification/Audit — внутренний HTTP.
- Каждый сервис имеет собственную БД или отдельную схему; прямые запросы между БД сервисов запрещены.
- Для надежной публикации событий используется outbox-паттерн.
- События доставляются минимум один раз; потребители идемпотентны.
- Ошибки доставки повторяются; после лимита попадают в очередь ошибок.
- Ссылки между сущностями разных сервисов — по идентификаторам, без внешних ключей между БД.
- Допускается eventual consistency; пользователь видит актуальные данные после короткой задержки.
- Для gRPC используются protobuf-контракты, дедлайны, retry, circuit breaker и межсервисная аутентификация.
- Сервисные gRPC-контракты версионируются и проверяются контрактными тестами.

### 3.4. Frontend: Vue 3 + Nuxt 3 с SSR

- **Vue 3 + Nuxt 3 с SSR**, JavaScript, без TypeScript.
- SSR используется для:
  - страниц входа, регистрации и восстановления пароля;
  - списка проектов и диаграмм;
  - начальной загрузки данных;
  - защиты маршрутов и работы с сессией.
- Интерактивная диаграмма Ганта гидрируется на клиенте.
- Состояние — Pinia.
- Запросы — через API Gateway по REST/JSON; сессия в HTTP-only cookie.
- WebSocket/SSE — через Sync Service.
- Frontend не обращается к базам данных и внутренним сервисам напрямую.
- Frontend не вызывает backend-сервисы по gRPC; gRPC — внутренний протокол backend.

### 3.5. Разделение frontend и backend

| Аспект | Backend | Frontend |
|--------|---------|----------|
| Технология | Node.js, JavaScript, микросервисы | Vue 3 + Nuxt 3, SSR, JavaScript |
| Роль | API, бизнес-правила, данные, права, уведомления | SSR-страницы, интерфейс, работа с API |
| Развертывание | Набор независимых сервисов | Отдельный SSR-сервис |
| Доступ к БД | Только у соответствующего сервиса | Нет |
| Аутентификация | User & Access Service + проверка в Gateway/сервисах | Вход, cookie-сессия, защита маршрутов |
| Публичный контракт | REST/JSON через API Gateway | REST/JSON |
| Внутренний контракт | gRPC/protobuf | Не используется |
| События | Брокер сообщений | WebSocket/SSE через Sync Service |

### 3.6. Инфраструктура и эксплуатация

- Контейнеры Docker; production — Kubernetes (рекомендуется) или Docker Compose для пилота.
- API Gateway/Ingress с TLS.
- PostgreSQL: **один кластер**, отдельные БД на сервис и отдельные схемы внутри каждой БД для будущего разделения; прямой доступ между схемами сервисов запрещён.
- Redis не хранит сессии: источник сессий — PostgreSQL User & Access Service (ADR-004). Rate limit, кэш и presence — предусмотренные роли Redis; факт использования конкретным сервисом сверяется с кодом.
- Брокер сообщений: Kafka (ADR-001); локальный Compose topic и fallback приложений различаются, см. `docs/IMPLEMENTATION-STATUS.md`.
- SMTP и Telegram Bot API.
- Секреты — в защищенном хранилище.
- Наблюдаемость: OpenTelemetry, метрики, логи, трассировка, алерты.
- gRPC health-check и readiness для каждого сервиса.
- CI/CD отдельно для каждого сервиса.
- Резервное копирование каждой БД и кластера.
- Сетевые политики: внутренние сервисы доступны только по gRPC внутри кластера.
- Для аналитики — отдельная read-only роль на основном кластере; read replica не требуется; доступ через обычные аналитические представления; отдельное маскирование не требуется.

## 4. Модель данных по сервисам

### 4.1. Владение данными

| Сервис | Данные |
|--------|--------|
| User & Access Service | Пользователи, учетные данные, сессии, профили, глобальные роли, приглашения, участники проектов, роли в проектах, каталог исполнителей, email, Telegram, связь пользователь–исполнитель |
| Project / Diagram Service | Проекты, диаграммы, задачи, подзадачи, зависимости, стили связей, комментарии, праздники, признаки БП/СП, номер Jira; ссылки на пользователей и исполнителей только по ID |
| Notification Service | Уведомления, настройки уведомлений, журнал доставки |
| Audit Service | Журнал аудита; ссылки на пользователей по ID |
| Sync / Realtime Service | Только подключения и подписки; бизнес-данные не хранит |

### 4.2. Правила

- Каждый сервис владеет своими данными и не читает чужие таблицы.
- **Все пользовательские сущности принадлежат только User & Access Service.**
- Project / Diagram Service не содержит профилей, имен, email, Telegram, ролей, участников проектов и каталога исполнителей.
- Project / Diagram Service хранит только идентификаторы пользователей и исполнителей как ссылки.
- Имена, email и Telegram для отображения и уведомлений получаются из User & Access Service по gRPC.
- Пользователь приложения и исполнитель — разные сущности; связь между ними хранится в User & Access Service.
- Задачи хранятся с UUID и отображаемым WBS-номером.
- Зависимости и стили связей хранятся отдельными записями.
- В задаче сохраняется только текстовый номер Jira; внешняя интеграция отсутствует.
- Для задачи поддерживается ответственный, исполнитель и **до двух соисполнителей**.
- Все изменения попадают в Audit Service через события.
- Данные для уведомлений получаются из событий Project / Diagram Service и сведений User & Access Service.
- История изменений диаграмм и аудит хранятся **2 месяца**.
- Состояние сворачивания и фильтры хранятся только на клиенте; шаблоны проектов и диаграмм не предусмотрены.
- Пользователь удаляется полностью; проект перед удалением переводится в архив.

## 5. Серверная база данных и синхронизация

### 5.1. Задачи

- Спроектировать БД Project / Diagram Service без пользовательских таблиц.
- Реализовать API чтения и изменения плана.
- Перенести локальные планы.
- Обеспечить доступ с разных устройств.
- Реализовать синхронизацию через Sync Service.
- Реализовать ревизии и обработку конфликтов.
- Настроить хранение истории изменений, аудита, уведомлений и журнала доставки — 2 месяца.
- Реализовать архивирование проекта перед удалением.
- Реализовать восстановление удаленного проекта в течение 1 года и последующую очистку.
- Обеспечить резервное копирование.
- Предоставить read-only доступ для аналитики без возможности изменения данных.

### 5.2. Требования

- Пользователь видит доступные проекты и диаграммы.
- План загружается через API Gateway и кэшируется на устройстве.
- Изменения задач, дат, статусов, зависимостей и комментариев сохраняются на сервере.
- Другое устройство пользователя видит изменения после синхронизации.
- Участники проекта видят изменения друг друга в режиме, близком к реальному времени.
- При конфликте пользователь получает понятное сообщение и выбор действия.
- Есть индикатор состояния: сохранено, сохраняется, ошибка, нет связи.
- При потере связи введенные данные не теряются бесследно.

### 5.3. Поток изменения

1. Frontend отправляет REST-запрос в API Gateway.
2. API Gateway проверяет сессию через User & Access Service по gRPC.
3. API Gateway маршрутизирует запрос в Project / Diagram Service по gRPC.
4. Project / Diagram Service проверяет членство и роль через User & Access Service по gRPC.
5. Сервис применяет изменение и сохраняет новую ревизию.
6. В той же транзакции записывается событие в outbox.
7. Событие публикуется в брокер.
8. Sync Service рассылает изменение подключенным клиентам.
9. Notification Service создает уведомления по правилам.
10. Audit Service фиксирует действие.

### 5.4. Синхронные вызовы и авторизация

- API Gateway вызывает User & Access Service по gRPC для проверки сессии.
- Project / Diagram Service вызывает User & Access Service по gRPC для проверки членства и роли.
- Результаты проверки прав могут кратковременно кэшироваться.
- Для gRPC задаются дедлайны; при недоступности User & Access Service операции изменения не выполняются.
- Допускается деградация только для необязательных функций: presence, аудит, уведомления.
- REST-вызовы между backend-сервисами запрещены.
- Внутренние gRPC-порты не публикуются наружу.

### 5.5. Правила синхронизации

1. Сервер хранит актуальную версию диаграммы и задачи.
2. Клиент отправляет изменения с версией, на основе которой они сделаны.
3. При устаревшей версии сервер сообщает о конфликте.
4. Конфликт разрешается пользователем; молчаливая потеря изменений запрещена.
5. Комментарии добавляются независимо и не конфликтуют.
6. События доставляются через брокер и Sync Service.
7. При повторном подключении клиент догружает изменения с последней известной версии.
8. Удаление задачи при одновременном редактировании требует явного решения.

### 5.6. Критерии приемки

- Один план открывается на двух устройствах.
- Изменение статуса на одном устройстве появляется на другом.
- Одновременное редактирование разных задач не теряет данные.
- Конфликт отображается и разрешается явно.
- Локальный план импортируется без потери задач, ответственных, комментариев, зависимостей и стилей связей.
- При потере сети пользователь видит статус и не теряет уже введенные данные.
- Падение Notification Service или Audit Service не блокирует сохранение плана.
- Project / Diagram Service не содержит пользовательских таблиц.
- Задача поддерживает до двух соисполнителей.
- Проект удаляется только после архивирования.
- Удаленный проект можно восстановить в течение 1 года; после этого он очищается.
- Хранится только последнее архивное состояние проекта.
- История изменений, аудит, уведомления и журнал доставки доступны за 2 месяца.
- Аналитика имеет read-only доступ и не может изменить данные.

- Сервисы доверяют только подписанным токенам/сессиям и внутренним service-токенам.

- Все пользовательские данные находятся только в User & Access Service.

## 7. Уведомления

### 7.1. Каналы

Только три канала:

1. Внутренние уведомления в приложении.
2. Email.
3. Telegram.

### 7.2. События

- назначение или смена ответственного, исполнителя, соисполнителей (до двух);
- приближение срока;
- просрочка;
- перевод задачи в «Заблокировано»;
- завершение задачи;
- новый комментарий или упоминание;
- нарушение зависимости;
- изменение критического пути;
- приглашение в проект.

### 7.3. Работа сервиса

- Notification Service подписывается на события Project / Diagram Service.
- Создает внутренние уведомления.
- Отправляет email через SMTP.
- Отправляет сообщения через Telegram-бота.
- Получает email, Telegram и сведения о пользователе из User & Access Service по gRPC.
- Пользователь настраивает события и каналы.
- Есть тихие часы и часовой пояс.
- Есть немедленные уведомления и дайджест.
- Одинаковые события не дублируются.
- Ошибки доставки повторяются с ограничением.
- Telegram подключается через привязку учетной записи к боту.
- Если исполнитель не является пользователем приложения, уведомление получает ответственный или владелец проекта.
- Все доставки фиксируются в журнале.

### 7.4. Критерии приемки

- Пользователь получает внутреннее уведомление о назначении задачи.
- Пользователь получает письмо и сообщение в Telegram по выбранным событиям.
- Пользователь может отключить ненужный канал.
- Повторные события не создают спам.
- При недоступности Telegram уведомление не теряется и повторяется.
- Email доставляется через настроенный SMTP.
- Недоступность Notification Service не влияет на сохранение плана.

## 11. Безопасность, надежность и эксплуатация

- Собственная аутентификация; пароли хранятся только в виде хеша.
- Сессии в HTTP-only cookie; защита от CSRF и перебора.
- API Gateway проверяет аутентификацию; сервисы проверяют права.
- Внутренние сервисы недоступны извне; gRPC только внутри кластера.
- Межсервисная аутентификация: mTLS и/или service-токены в gRPC metadata.
- Сетевые политики между сервисами.
- **Средний уровень шифрования:** TLS 1.2+ для передачи, шифрование дисков и резервных копий, хеширование паролей (Argon2id/bcrypt) и токенов; отдельное шифрование каждого поля не требуется.
- Секреты SMTP и Telegram — в защищенном хранилище.
- Ограничение частоты запросов.
- Аудит входов, изменений плана, прав и уведомлений; общий журнал — 2 месяца, привилегированный журнал администраторов — 2 года.
- Выгрузка журнала аудита не предусмотрена.
- Уведомления и журнал доставки хранятся 2 месяца.
- Удаленный проект хранится 1 год с возможностью восстановления; после истечения срока очищается.
- Резервное копирование БД каждого сервиса и кластера; проверка восстановления.
- Целевые показатели: RPO — не более 24 часов, RTO — не более 4 часов (уточняются).
- Мониторинг доступности, ошибок API, gRPC, очередей, событий и доставки уведомлений.
- Трассировка запросов между сервисами, включая gRPC.
- Обработка недоступности сервисов: дедлайны, повторные попытки, circuit breaker, очередь ошибок.
- Соблюдение применимых требований к персональным данным.
- Возможность экспорта и полного удаления данных пользователя; перед удалением владение проектами передается другому пользователю.
- Отдельная read-only роль для аналитики на основном кластере; доступ через представления, без права записи; read replica и обязательное маскирование не требуются.

## 13. Риски и меры

| Риск | Влияние | Мера |
|------|---------|------|
| Сложность микросервисной архитектуры | Рост сроков и стоимости | Минимальный набор сервисов, без избыточного дробления |
| Сложность gRPC/protobuf | Ошибки контрактов и задержки | Contract-first, codegen, contract-тесты, версионирование |
| Связность Project / Diagram Service с User & Access Service | Задержки и отказы авторизации | Кэш проверок, дедлайны, retry, circuit breaker |
| Несогласованность данных между сервисами | Ошибки в плане | Outbox, идемпотентность, события, контрактные тесты |
| Сложность отладки | Дольше поиск ошибок | Трассировка, единые логи, correlation id |
| Сложность собственной авторизации | Риск безопасности | Проверенные библиотеки, хеширование, аудит, тесты |
| Проблемы доставки email | Пользователь не получает уведомления | Надежный SMTP, мониторинг, повтор, резервный канал |
| Ограничения Telegram | Недоставка | Повтор, журнал, альтернативные email/внутренние уведомления |
| Сложность конфликтов синхронизации | Потеря данных | Ревизии, явные конфликты, аудит |
| Трудоемкость SSR-переписывания | Срыв сроков | Поэтапный перенос экранов, приоритет диаграммы и входа |
| Рост инфраструктурных затрат | Дороже эксплуатация | Kubernetes, автоматизация, мониторинг затрат |
| Сопротивление пользователей | Низкое внедрение | Пилот, обучение, сохранение привычного интерфейса |
| Утечка секретов | Безопасность | Хранилище секретов, ротация, аудит |
| Потеря данных при миграции | Потеря плана | Экспорт перед миграцией, проверка, откат |

## 16. Критерии готовности программы

1. Приложение разворачивается самостоятельно.
2. Backend состоит из независимо развертываемых сервисов.
3. Все пользовательские данные, роли, участники проектов и исполнители находятся только в User & Access Service.
4. Project / Diagram Service не содержит пользовательских таблиц и профилей.
5. Backend-сервисы синхронно общаются только по gRPC; REST между ними отсутствует.
6. Публичный API frontend → API Gateway работает по REST/JSON.
7. Пользователь регистрируется и входит в приложение.
8. Роли и участие в проекте ограничивают доступ к действиям.
9. Один план доступен на нескольких устройствах.
10. Изменения синхронизируются, конфликты не теряют данные.
11. Пользователь получает внутренние уведомления, email и сообщения в Telegram.
12. В карточке задачи можно указать номер Jira без интеграции с Jira.
13. Недоступность уведомлений или аудита не блокирует работу с планом.
14. Есть аудит, резервное копирование и мониторинг.
15. Локальные планы перенесены без потери ключевых данных.
16. Проект можно архивировать и удалить только после архивирования.
17. Удаленный проект можно восстановить в течение 1 года; после этого он очищается.
18. Хранится только последнее архивное состояние проекта.
19. Пользователь удаляется полностью, владение проектами передается заранее.
20. История изменений, общий аудит, уведомления и журнал доставки хранятся 2 месяца; привилегированный аудит администраторов — 2 года.
21. Выгрузка журнала аудита отсутствует.
22. Задача поддерживает до двух соисполнителей.
23. Состояние сворачивания и фильтры не хранятся на сервере; шаблонов нет.
24. Аналитика имеет read-only доступ на основном кластере; read replica, материализованные представления и обязательное маскирование не используются.
25. Пилотная группа подтвердила работоспособность и удобство.
