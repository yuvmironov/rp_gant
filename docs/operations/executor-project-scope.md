# Назначения задач участникам проекта

Роли задач `executor` (Исполнитель) и `co_executor` (Соисполнитель, не более двух) остаются. Они назначаются только пользователям со статусом active, состоящим в активных участниках соответствующего проекта. Удалённый каталог исполнителей не создаёт учётные записи и членство: приглашайте пользователей через страницу «Участники проекта».

В импортах старых JSON/CSV однозначное имя сопоставляется с единственным активным участником проекта (без учёта регистра и внешних пробелов). UUID принимается только если он является ID активного участника. Неоднозначные или неизвестные имена/ID остаются неназначенными и возвращаются в `report.issues` как предупреждения, например `executor_not_mapped:<task>:<value>`; каталоговые assignee types не импортируются.

## Миграция схемы

Миграции `project_diagram/0009_user_only_task_assignments.sql` и `user_access/0005_remove_executor_catalog.sql` forward-only. Сначала project migration проверяет, что в `plan.assignments` не осталось строк с `assignee_type='executor'`, и заменяет constraint на user-only. Только после её успеха удаляются `access.executor_projects` и `access.executors`. Локальный bootstrap соблюдает этот порядок.

Если guard обнаруживает legacy assignments, миграция намеренно останавливается без изменения схемы. Подготовьте и проверьте отдельный план преобразования/удаления затронутых назначений на staging; не отключайте guard и не запускайте последующую user migration отдельно. Перед production rollout необходимы staging acceptance, backup и отдельное согласование deployment.
